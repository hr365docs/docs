    Approval Workflow: An Approval Workflow in CLM365 defines the sequence of steps or stages that a contract goes through for approval. It outlines the process, specifies approvers, and determines actions necessary for a contract's approval.


    Clause Library: The Clause Library is a centralized repository within CLM365 that stores reusable legal clauses. Users can select predefined clauses while drafting contracts, ensuring consistency and reducing drafting time.


    When you click + Add in the Clause Library, a new clause creation form opens. This interface allows users to define reusable clauses by specifying the type, name, tags, and clause content using a rich text editor.


    To create a new clause, select the appropriate Clause Type, enter a unique Clause Name, add relevant Tags for easy search, and provide the full Clause content. You may also assign a Clause Title and optionally create an Alternate Clause for variations.


    Clause Type: Clause Types help categorize clauses in the Clause Library, such as indemnity clauses, termination clauses, confidentiality clauses, etc. These types assist in organizing and retrieving clauses based on their legal function or relevance.


    Contract Type: Contract Types in CLM365 categorize contracts based on their nature or purpose, such as sales contracts, service agreements, non-disclosure agreements (NDAs), etc. Each type might have specific templates, clauses, or processes associated with it.

    Counter Party: The Counterparty section in CLM365 enables you to manage external parties involved in contracts. It supports both individual and bulk additions for streamlined contract collaboration and tracking.


    Counterparty Type: Counterparty Types classify different types of counterparties based on their nature, such as customers, vendors, partners, etc. This classification helps in segmenting and managing contracts associated with different counterparties.


    Document Type: Document Types categorize documents related to contracts, such as proposals, amendments, addendums, etc. It helps in organizing and managing various document types associated with contracts.


    Obligations represent the specific actions, tasks, or responsibilities outlined in a contract that must be fulfilled by either party. This module helps track and manage these commitments efficiently throughout the contract lifecycle.


    Clicking + Add in the Obligations section opens the Add Obligation form, where you define the obligation's title, contract type, category, priority, status, and description. Use Save to submit or Save and Add More to continue adding obligations.


    Obligation Type categorizes each obligation (e.g., Compliance, Payment, Delivery) to streamline tracking, reporting, and reminder workflows, ensuring clarity and accountability.


    Organization Info: Organization Info typically includes essential information about the parties involved in contracts, such as their legal names, addresses, contact details, and other pertinent information.


    Reasons: Reasons might refer to predefined reasons or justifications associated with certain actions or events related to contracts, such as contract terminations, renewals, amendments, etc.


    Custom Actions from Request Action Menu

    Users can create their own custom actions directly from the Request Action menu. By selecting Action from the request options, you can configure and define actions based on:

    • User Roles
    • Approval Flow Requirements
    • Specific Business Processes

    This allows organizations to tailor actions according to their internal workflow and ensure that the correct approval process is followed for each role.



    Creating a New Action from the Actions Panel

    To create a new custom action, follow the steps below:

    1. Navigate to the Request Action menu.
    2. Click on Actions to create a new action.

    Once you click Actions, the Action Panel will open.

    1. In the panel, select the Request Stage from the dropdown menu.

      The available request stages include:

      • Draft Approval
      • Business Approval
      • Execution Approval
      • Legal Review
      • Negotiation
    2. After selecting the request stage, choose the Role for which the action should be displayed.

      This ensures that the action is only visible to the appropriate users based on their role and the selected approval stage.

    3. For each request stage, choose the appropriate Stage Status.

      The available status options are:

      • Not Started
      • Pending
      • Completed

      This allows actions to appear only when the request is in the correct status.

    4. Next, select the Request Actions that should be available for the chosen role and stage.

      Some of the available request actions include:

      • Edit Request
      • Withdraw Request
      • Upload Draft
      • Print Draft
      • Execution Approval
      • Send for Legal Review
      • Negotiation
      • Publish

      You can select multiple actions based on your workflow requirements.
      This configuration ensures that users see only the relevant actions depending on their role, the current stage, and the request status.



    5. Once all selections are completed, click Save to create and apply the new action configuration.

    After saving the action configuration, the selected actions will become available based on the setup you created.

    When an approver is reviewing and approving a task, the Action options will be automatically enabled according to:

    • The configured Request Stage
    • The selected Stage Status
    • The assigned User Role
    • The chosen Request Actions

    This ensures that approvers can only perform the actions that are relevant to their role and the current workflow stage.

    Post Rejection

    For approval stages that include more than one approval level, an additional configuration option is available:

    “Post rejection, redirect the task to”

    This option defines where the task should be sent if it is rejected during the approval process.

    Available Redirection Options

    • Previous Levels: Redirects the task back to the earlier approval levels for re-review.
    • Business User: (Applicable for Request Approval stages) Sends the rejected task back to the business user who initiated the request.
    • Contract Owner: (Applicable for Contract Approval stages) Sends the rejected task back to the contract owner for further action.






    Post Rejection Scenarios

    When the Post rejection, redirect the task to option is configured, the rejection behavior changes based on the selected redirection target.

    Case 1: No Option Selected (Default Behavior)

    When no redirection option is configured, the system follows the default rejection handling based on the approval level.

    1. Business Approval

    • Level 1: If a rejection occurs at Level 1, the approval flow stops at this stage. The Business User (Requester) is allowed to edit the request, and once updated, the approval workflow is triggered again from the beginning.











    • Level 2 or Above: If a rejection occurs at Level 2 or higher, a task is automatically created for the previous approval level, and the approval process continues normally from that earlier stage.





    2. Legal Review

    • If a rejection occurs during the Legal Review stage, a Business Approval – Level 1 task is automatically created on rejection, and the approval workflow then continues as per the standard process.







    3. Draft Approval

    Rejection handling in the Draft Approval stage depends on the approval level:

    • Level 1: If a rejection occurs at Draft Approval – Level 1, a Legal Review task is created and the approval workflow continues as usual from that stage.









    • Level 2 or Above: If a rejection occurs at Draft Approval – Level 2 or higher, a task is created for the previous approval level, and the workflow continues normally through the approval process.







    4. Execution Approval

    Rejection handling in the Execution Approval stage depends on the approval level:

    • Level 1: If a rejection occurs at Execution Approval – Level 1, a Legal Review task is created, and the approval workflow then continues as usual from the Legal Review stage.







    • Level 2 or Above: If a rejection occurs at Execution Approval – Level 2 or higher, the system creates a task of the previous approval level, and the approval workflow continues as usual from that level.







    5. eSign & Publish Stages

    • eSign: Rejection is not allowed in the eSign stage. Tasks in this stage cannot be rejected.
    • Publish: Rejection is not allowed in the Publish stage. The workflow does not support rejection at this stage.

    6. Contract Approval

    Rejection handling in the Contract Approval stage depends on the approval level:

    • Level 1: If a rejection occurs at Contract Approval – Level 1, the approval flow stops at this stage. The Contract Owner is allowed to edit the request, and once updated, the approval workflow is re-triggered.











    • Level 2 or Above: If a rejection occurs at Contract Approval – Level 2 or higher, the previous level task is created, and the approval process continues as usual from that level.







    Case 2: “Post rejection, redirect the task to” Option Selected

    General Rule: If “Business User” Is Selected at Any Stage

    When Business User is chosen as the redirection option, if the task is rejected at any stage, the request is redirected back to the Business User (Requester). The Requester is allowed to edit and update the request. Once the update is completed, the approval workflow is re-triggered.



    • Business Approval – Level 1: For Business Approval – Level 1, the rejection behavior remains the same as the default. The approval flow stops at this stage, the Requester (Business User) can edit the request, and after the update, the approval workflow is re-triggered.









    • Business Approval – Level 2 or Above: If a rejection occurs at Business Approval – Level 2 or higher, the task is redirected and assigned to the approval level selected in the “Post rejection, redirect the task to” configuration, and the workflow then continues as usual from that stage.



    • Legal Review: If a rejection occurs during the Legal Review stage, the task is redirected and assigned to Business Approval – Level 1, and the approval workflow then continues as usual from that stage.







    • Draft Approval: Rejection handling depends on the level:
      • Level 1: If a rejection occurs at Draft Approval – Level 1, the task is redirected and assigned to the Legal Review stage, and the approval workflow then continues as usual from that stage.
      • Level 2 or Above: If a rejection occurs at Draft Approval – Level 2 or higher, the task is redirected and assigned to the approval level selected in the configuration, and the workflow continues as usual from that stage.



    • Execution Approval: Rejection handling depends on the level:
      • Level 1 (As Default Flow): If a rejection occurs at Execution Approval – Level 1, the task is redirected and assigned to the Legal Review stage, and the approval workflow then continues as usual from that stage.
      • Level 2 or Above: If a rejection occurs at Execution Approval – Level 2 or higher, the task is redirected and assigned to the approval level selected in the configuration, and the workflow continues as usual from that stage.



    • eSign & Publish Stages:
      • eSign: Rejection is not allowed in the eSign stage. Tasks in this stage cannot be rejected or redirected.
      • Publish: Rejection is not allowed in the Publish stage. The workflow does not support rejection at this stage.

    General Rule: If “Contract Owner” Is Selected at Any Stage

    When Contract Owner is chosen as the redirection option, if the task is rejected at any stage, the contract is redirected back to the Contract Owner. The Contract Owner is allowed to edit and update the contract. Once the update is completed, the approval workflow is re-triggered.

    • Contract Approval: Rejection handling depends on the level:
      • Level 1: If a rejection occurs at Contract Approval – Level 1, the approval flow stops at this stage. The Contract Owner is allowed to edit the request, and after the update, the approval workflow is re-triggered.
      • Level 2 or Above: If a rejection occurs at Contract Approval – Level 2 or higher, the task is redirected and assigned to the approval level selected in the “Post rejection, redirect the task to” configuration, and the workflow then continues as usual from that stage.
